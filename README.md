# Backtester V2 - Инструкции по установке и запуску (Этап 0-1)

Этот документ описывает шаги для настройки, запуска и базовой проверки функционала приложения Backtester V2, разработанного на Этапах 0 и 1.

## Предварительные требования

Перед началом убедитесь, что у вас установлены:

*   **Docker**: [Инструкция по установке Docker](https://docs.docker.com/engine/install/)
*   **Docker Compose**: Обычно устанавливается вместе с Docker Desktop. [Инструкция](https://docs.docker.com/compose/install/)
*   **Node.js**: Рекомендуется LTS версия. [Скачать Node.js](https://nodejs.org/)
*   **npm**: Обычно устанавливается вместе с Node.js.

## Установка

1.  **Клонируйте репозиторий** (если вы еще этого не сделали):
    ```bash
    git clone <repository_url>
    cd backtesterv2
    ```
2.  **Установите зависимости** (хотя они уже должны быть установлены в процессе разработки, на всякий случай):
    ```bash
    # В корневой директории проекта
    cd backend
    npm install
    cd ../frontend
    npm install
    cd ..
    ```
3.  **(Важно) Создайте файл `.env` для Backend:**
    *   Перейдите в директорию `backend`.
    *   Попробуйте скопировать файл `.env.example` (если он был создан автоматически) и переименовать копию в `.env`:
        ```bash
        # Находясь в директории backend
        cp .env.example .env
        ```
    *   **Если `.env.example` не был создан автоматически** (из-за возможных ограничений безопасности), создайте файл `backend/.env.example` и `backend/.env` вручную со следующим содержимым:
        ```dotenv
        NODE_ENV=development
        PORT=5000
        
        # PostgreSQL Database (значения используются, если не переопределены в docker-compose)
        DB_HOST=db
        DB_PORT=5432
        DB_USERNAME=user
        DB_PASSWORD=password
        DB_DATABASE=backtester_db
        
        # Redis (значения используются, если не переопределены в docker-compose)
        REDIS_HOST=redis
        REDIS_PORT=6379
        
        # OKX API (Optional - for future use if needed beyond public data)
        # OKX_API_KEY=
        # OKX_API_SECRET=
        # OKX_API_PASSPHRASE=
        ```
    *   **Примечание:** В текущей конфигурации `docker-compose.yml` переменные окружения для базы данных и Redis уже заданы в секции `environment` сервиса `backend`. Файл `.env` пока не используется напрямую Docker'ом (строка `volumes` закомментирована), но он нужен для локальной разработки и может понадобиться в будущем. Убедитесь, что значения в `docker-compose.yml` соответствуют вашим ожиданиям.

## Запуск приложения

Проект использует Docker Compose для управления окружением.

### Режим Разработки (с Hot Reloading для Frontend)

1.  Убедитесь, что Docker Desktop запущен.
2.  В корневой директории проекта выполните:
    ```bash
    docker-compose -f docker-compose.yml -f docker-compose.override.yml up --build
    ```
    *   Флаг `--build` нужен при первом запуске или после изменений в `Dockerfile`, `package.json` или базовых зависимостях.
    *   В последующие разы можно использовать `docker-compose -f docker-compose.yml -f docker-compose.override.yml up`.
3.  **Frontend** будет доступен на [http://localhost:5173](http://localhost:5173) с включенным Hot Module Replacement (HMR) благодаря Vite.
4.  **Backend API** доступен на [http://localhost:5000](http://localhost:5000). Запросы от Frontend (с `localhost:5173`) будут проксироваться на бэкенд благодаря настройке в `frontend/vite.config.ts`.

### Режим Production (сборка Frontend и раздача через Nginx)

1.  Убедитесь, что Docker Desktop запущен.
2.  В корневой директории проекта выполните:
    ```bash
    docker-compose up --build
    ```
    *   Эта команда использует только `docker-compose.yml`.
    *   Frontend будет собран с помощью `npm run build` и будет раздаваться через Nginx.
3.  **Frontend** будет доступен на [http://localhost:8080](http://localhost:8080).
4.  **Backend API** доступен на [http://localhost:5000](http://localhost:5000).

## Остановка приложения

*   Нажмите `Ctrl + C` в терминале, где запущен `docker-compose`.
*   Для остановки и удаления контейнеров: `docker-compose down` (если запускали production) или `docker-compose -f docker-compose.yml -f docker-compose.override.yml down` (если запускали development).
*   Для удаления контейнеров и томов (volumes): добавьте флаг `-v` к команде `down`.

## Dockerfiles

В проекте используются следующие Dockerfile для контейнеризации приложений:

*   **`backend/Dockerfile`**: Отвечает за сборку и запуск Node.js бэкенд-приложения.
    *   Использует многоэтапную сборку.
    *   На первом этапе устанавливает зависимости и компилирует TypeScript (если применимо).
    *   На втором этапе копирует скомпилированное приложение и запускает его.
*   **`frontend/Dockerfile`**: Отвечает за сборку Vue.js фронтенд-приложения и его сервировку через Nginx.
    *   **Этап 1 (`builder`)**: Использует образ `node:lts-alpine`.
        *   Устанавливает зависимости `npm install`.
        *   Собирает статические файлы приложения `npm run build`.
    *   **Этап 2**: Использует образ `nginx:stable-alpine`.
        *   Копирует собранные статические файлы из этапа `builder`.
        *   Запускает Nginx для раздачи статики на порту 80.

Для разработки фронтенда с hot-reloading используется `docker-compose.override.yml`, который переопределяет команду запуска контейнера `frontend` на `npm run dev -- --host` и монтирует локальные исходные файлы в контейнер.

## Работа с Git и GitLens в VS Code

Эта секция расширяет предыдущую, фокусируясь на использовании Git в связке с популярным расширением VS Code - **GitLens**. GitLens значительно улучшает визуализацию и взаимодействие с Git-репозиторием прямо в редакторе.

### Основной цикл работы

Классический цикл работы с Git состоит из следующих шагов:

1.  **Модификация:** Вы изменяете файлы в вашем проекте (пишете код, правите текст и т.д.).
2.  **Индексация (Staging):** Вы выбираете, какие измененные файлы вы хотите включить в следующий коммит. Это называется добавлением в индекс или "стейджингом".
3.  **Коммит (Commit):** Вы сохраняете "снимок" проиндексированных изменений в истории репозитория с осмысленным сообщением, описывающим сделанные изменения.
4.  **Отправка (Push):** (При работе с удаленным репозиторием) Вы отправляете ваши локальные коммиты на удаленный сервер (например, GitHub, GitLab), чтобы поделиться ими с командой или сохранить резервную копию.

### Сохранение изменений с GitLens

1.  **Откройте панель Source Control:** Нажмите на иконку Git на левой панели VS Code или используйте сочетание клавиш `Ctrl+Shift+G`.
2.  **Просмотрите изменения:** В секции "Changes" вы увидите список всех измененных, добавленных или удаленных файлов с момента последнего коммита.
3.  **Индексация (Staging):**
    *   Чтобы добавить *один* файл в индекс, наведите на него курсор и нажмите иконку `+` (Stage Changes).
    *   Чтобы добавить *все* измененные файлы в индекс, наведите курсор на заголовок "Changes" и нажмите иконку `+` (Stage All Changes).
    *   Проиндексированные файлы переместятся в секцию "Staged Changes".
4.  **Коммит:**
    *   В поле ввода "Message" над секцией "Changes" напишите краткое и понятное сообщение коммита (например, "Добавлена функция аутентификации", "Исправлена ошибка отображения цен").
    *   Нажмите галочку ✔️ (Commit) или используйте `Ctrl+Enter`.
    *   **Важно:** Коммитятся только файлы из секции "Staged Changes".

### Откат изменений с GitLens

GitLens и VS Code предоставляют удобные способы отмены изменений:

*   **Отменить неиндексированные изменения в файле:** В секции "Changes" наведите курсор на файл и нажмите иконку со стрелкой назад ↺ (Discard Changes). **Внимание:** Это действие необратимо удалит все ваши последние изменения в этом файле!
*   **Убрать файл из индекса (Unstage):** Если вы ошибочно добавили файл в "Staged Changes", наведите на него курсор и нажмите иконку `-` (Unstage Changes). Файл вернется в секцию "Changes".
*   **Отменить последний коммит (если он еще не отправлен):** Откройте палитру команд (`Ctrl+Shift+P`), найдите и выберите команду `Git: Undo Last Commit`. Это вернет файлы из последнего коммита в состояние "Staged Changes" или "Changes".
*   **Сбросить состояние до определенного коммита (Осторожно!):**
    *   В панели GitLens (обычно иконка GitLens на левой панели) перейдите в раздел "Commits".
    *   Найдите коммит, к которому хотите вернуться.
    *   Кликните правой кнопкой мыши по коммиту и выберите `Reset current branch to this Commit...`.
    *   Выберите режим сброса (`Soft`, `Mixed`, `Hard`). **`Hard` удалит все изменения после выбранного коммита безвозвратно!** Используйте с большой осторожностью.
*   **Восстановить предыдущую версию файла:**
    *   Откройте файл.
    *   В панели GitLens перейдите в раздел "File History".
    *   Найдите нужную версию файла в списке коммитов.
    *   Кликните правой кнопкой мыши и выберите `Restore (Checkout) Revision`. Или используйте иконки для сравнения версий. 

### Ключевые элементы интерфейса GitLens

*   **Source Control View (Ctrl+Shift+G):** Основная панель для индексации, коммита, просмотра изменений.
*   **GitLens View (Иконка GitLens):** Предоставляет детальные представления:
    *   **Commits:** Просмотр истории коммитов текущей ветки.
    *   **Repositories:** Обзор вашего репозитория, статуса, веток.
    *   **File History:** История изменений для текущего открытого файла.
    *   **Branches:** Просмотр, создание, переключение, слияние веток.
    *   **Remotes:** Информация об удаленных репозиториях.
    *   **Stashes:** Работа со "спрятанными" изменениями.
    *   **Tags:** Работа с метками версий.
*   **Inline Blame:** Справа от каждой строки кода GitLens показывает, кто и когда последний раз изменял эту строку. Наведение курсора дает больше деталей.
*   **Code Lens:** Над функциями, классами или блоками кода GitLens показывает информацию о последнем коммите, затронувшем этот блок, и количестве авторов.
*   **Status Bar:** В нижней строке состояния VS Code GitLens показывает текущую ветку, количество входящих/исходящих коммитов и др.

### Работа с ветками (Branches)

**Что такое ветки?** Представьте историю вашего проекта как дерево. Основной ствол - это главная ветка (часто `main` или `master`), содержащая стабильную версию. Ветки - это ответвления от этого ствола, позволяющие работать над новыми функциями или исправлениями, не затрагивая основную стабильную версию.

**Зачем нужны ветки?**

*   **Изоляция:** Разработка новой функции в отдельной ветке не сломает рабочий код в `main`.
*   **Параллельная работа:** Несколько разработчиков могут работать над разными задачами в своих ветках одновременно.
*   **Эксперименты:** Можно безопасно пробовать новые идеи в отдельной ветке.

**Работа с ветками в GitLens/VS Code:**

1.  **Просмотр веток:**
    *   Нажмите на имя текущей ветки в строке состояния VS Code (внизу слева).
    *   Или откройте панель GitLens -> Branches.
2.  **Создание новой ветки:**
    *   Нажмите на имя текущей ветки в строке состояния.
    *   Выберите `+ Create new branch...` или `+ Create new branch from...`.
    *   Введите имя новой ветки (например, `feature/user-login`, `fix/payment-bug`).
3.  **Переключение между ветками:**
    *   Нажмите на имя текущей ветки в строке состояния и выберите нужную ветку из списка.
    *   Или в панели GitLens -> Branches кликните правой кнопкой по нужной ветке и выберите `Switch to Branch`.
4.  **Слияние (Merge) веток:**
    *   Переключитесь на ветку, *в которую* вы хотите влить изменения (например, на `main`).
    *   Откройте палитру команд (`Ctrl+Shift+P`), найдите и выберите `Git: Merge Branch...`.
    *   Выберите ветку, *из которой* вы хотите взять изменения (например, `feature/user-login`).
    *   Git попытается автоматически слить изменения. Если возникнут **конфликты** (когда один и тот же участок кода изменен в обеих ветках), VS Code подсветит их и предложит инструменты для разрешения.
5.  **Отправка ветки на удаленный репозиторий:**
    *   Переключитесь на ветку, которую хотите отправить.
    *   Нажмите кнопку `Publish Branch` в строке состояния или на панели Source Control.
    *   Или используйте команду `Git: Push` (`Ctrl+Shift+P`). Если ветка публикуется впервые, может потребоваться команда `Git: Push to...` для указания удаленного репозитория (`origin`).
6.  **Удаление ветки:**
    *   В панели GitLens -> Branches кликните правой кнопкой по ветке, которую хотите удалить (убедитесь, что она слита и больше не нужна), и выберите `Delete Branch...`. Нельзя удалить ветку, на которой вы сейчас находитесь.

### Рекомендации

*   **Ветка `main` (или `master`) должна быть всегда рабочей.** Не делайте коммиты напрямую в нее, кроме как при слиянии готовых веток.
*   **Для каждой новой задачи (фича, багфикс) создавайте отдельную ветку** от актуального состояния `main`.
*   **Давайте веткам осмысленные имена** (например, `feature/shopping-cart`, `hotfix/critical-login-issue`).
*   **Регулярно обновляйте свою рабочую ветку** изменениями из `main`, чтобы избежать больших конфликтов при слиянии (`git pull origin main`, затем `git merge main` в вашей ветке, или используйте `git rebase main`).
*   **Перед слиянием ветки в `main`, убедитесь, что ваша ветка содержит последние изменения из `main`.**
*   **Удаляйте ветки после их слияния**, чтобы не засорять репозиторий.

Эта инструкция поможет вам эффективнее использовать Git и GitLens для управления версиями вашего проекта.

### Пример типового рабочего процесса (Feature Branch Workflow)

Этот пример показывает стандартный подход к добавлению новой функциональности или исправлению ошибки с использованием веток:

1.  **Убедитесь, что вы на основной ветке (`main`) и она актуальна:**
    ```bash
    git checkout main
    git pull origin main
    ```
2.  **Создайте новую ветку для вашей задачи:**
    ```bash
    git checkout -b feature/название-фичи # или fix/название-исправления
    ```
3.  **Работайте над задачей в новой ветке:** Вносите изменения, добавляйте файлы.
4.  **Делайте коммиты по мере выполнения:**
    ```bash
    git add .
    git commit -m "Понятное описание сделанного этапа работы"
    ```
5.  **(Опционально, но полезно) Отправьте вашу ветку на удаленный репозиторий:** Это создаст резервную копию и позволит другим видеть вашу работу (если нужно).
    ```bash
    git push -u origin feature/название-фичи
    ```
6.  **Когда задача завершена, вернитесь на основную ветку:**
    ```bash
    git checkout main
    ```
7.  **Снова обновите основную ветку:** (на случай, если кто-то другой внес изменения в `main`, пока вы работали)
    ```bash
    git pull origin main
    ```
8.  **Слейте вашу ветку с задачей в основную ветку:**
    ```bash
    git merge feature/название-фичи
    ```
    *Если возникнут конфликты, разрешите их, затем добавьте разрешенные файлы (`git add .`) и завершите слияние (`git commit`).*
9.  **Отправьте обновленную основную ветку на удаленный репозиторий:**
    ```bash
    git push origin main
    ```
10. **Удалите ветку задачи (после успешного слияния):**
    *   Локально:
        ```bash
        git branch -d feature/название-фичи
        ```
    *   На удаленном репозитории:
        ```bash
        git push origin --delete feature/название-фичи
        ```

Этот цикл повторяется для каждой новой фичи или исправления.
