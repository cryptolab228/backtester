### 1️⃣ **КРИТИЧНО: Проверка достаточности капитала**

**Проблема:** Капитал мог уходить в отрицательные значения при открытии сделки, если `requiredMargin + entryFee > currentCapital`.

**Решение:**  
Добавлена проверка ПЕРЕД блокировкой капитала во всех режимах:

#### Одиночный бэктестер (режим с подтверждением)
**Файл:** `backend/src/modules/backtester/backtester.ts`  
**Строки:** 359-368

```typescript
const totalRequired = requiredMargin + entryFee;

// ИСПРАВЛЕНО: Проверка достаточности капитала ПЕРЕД открытием
if (currentCapital < totalRequired) {
  logger.warn(`[RunBacktest] Insufficient capital for ${params.pairSymbol}. Required: ${totalRequired.toFixed(2)}, Available: ${currentCapital.toFixed(2)}. Signal skipped.`);
  pendingSignal = null;
  continue;
}
```

#### Одиночный бэктестер (режим без подтверждения)
**Файл:** `backend/src/modules/backtester/backtester.ts`  
**Строки:** 507-512

```typescript
// ИСПРАВЛЕНО: Проверка достаточности капитала ПЕРЕД открытием
if (currentCapital < totalRequired) {
  logger.warn(`[RunBacktest] Insufficient capital for ${params.pairSymbol}. Required: ${totalRequired.toFixed(2)}, Available: ${currentCapital.toFixed(2)}. Signal skipped.`);
  activeTrade = null;
  continue;
}
```

#### Портфельный бэктестер
**Файл:** `backend/src/modules/backtester/backtester.ts`  
**Строки:** 1259-1264

```typescript
// ИСПРАВЛЕНО: Проверка достаточности капитала ПЕРЕД открытием
if (updatedCapital < totalRequired) {
  signalsSkippedDueToCapital++;
  logger.warn(`[ProcessPortfolioSignals] Insufficient capital for ${signal.pairSymbol}. Required: ${totalRequired.toFixed(2)}, Available: ${updatedCapital.toFixed(2)}. Signal skipped.`);
  continue;
}
```

**Результат:**
- ✅ Невозможен отрицательный капитал
- ✅ Сделки корректно пропускаются при недостатке средств
- ✅ Логируются все пропуски из-за капитала

### 2️⃣ **КРИТИЧНО: Умножение на leverage после расчета риска**

**Проблема:** Размер позиции умножался на `leverage` ПОСЛЕ расчета на основе риска, что нарушало логику риск-менеджмента.

**Пример ошибочного поведения:**
```
Рассчитанный размер на риск 2%: size = 2.0
После умножения на leverage=5: size = 10.0
Реальный риск при SL: 10% вместо 2% ❌
```

**Решение:**  
Убрано умножение на leverage в режиме с подтверждением.

**Файл:** `backend/src/modules/backtester/backtester.ts`  
**Строки:** 355-356

**Было:**
```typescript
const positionSizeBase = calculatePositionSize(currentCapital, fillPrice, confirmCandle, riskSettings);
const size = positionSizeBase * Math.max(executionProfile.leverage, 1); // ❌ ОШИБКА
```

**Стало:**
```typescript
// ИСПРАВЛЕНО: Убрано умножение на leverage - размер уже учитывает риск
const positionSize = calculatePositionSize(currentCapital, fillPrice, confirmCandle, riskSettings);
```

**Результат:**
- ✅ Риск соблюдается согласно `maxRiskPerTradePercentage`
- ✅ Leverage учитывается только в расчете маржи
- ✅ Математика риск-менеджмента корректна

**Примечание:** В режиме без подтверждения и в портфельном бэктестере умножения на leverage уже не было.

**Решение:**

**Файл:** `backend/src/modules/backtester/backtester.ts`  
**Строки:** 336-341

  const signalDir = currentCandle.entryConditionLong ? 'LONG' : 'SHORT';

  logger.debug(`[RunBacktest] Signal SKIPPED for ${params.pairSymbol} (${signalDir}, strength: ${signalStrength.toFixed(2)}) - Active trade exists (${activeTrade?.direction || 'unknown'})`);
}

### 4️⃣ **ВАЖНО: Идеальный ExecutionProfile**

**Проблема:** По умолчанию применялся `DEFAULT_EXECUTION_PROFILE` с комиссиями 0.06% и плечом 10, что не соответствовало "идеальному режиму".

**Решение:**  
Создан новый профиль для тестирования без комиссий и плеча.

**Файл:** `backend/src/modules/execution/executionProfile.ts`  
**Строки:** 24-31

```typescript
// НОВОЕ: Идеальный профиль для режима без комиссий, плеча и проскальзывания
export const IDEAL_EXECUTION_PROFILE: ExecutionProfile = {
  tradingFeeRate: 0,      // Без комиссий
  leverage: 1,            // Без плеча
  slippageBps: 0,         // Без проскальзывания
  confirmWindowSize: 1,
  maxConfirmationAttempts: 1,
};
```

**Использование:**
```typescript
import { IDEAL_EXECUTION_PROFILE } from '../execution/executionProfile';

const result = await runBacktest({
  ...params,
  executionProfile: IDEAL_EXECUTION_PROFILE
});
```

**Результат:**
- ✅ Доступен явный профиль для "чистого" тестирования
- ✅ Можно легко переключаться между режимами
- ✅ Документирован и экспортирован

### 5️⃣ **ВАЖНО: Синхронизация схемы session_id**

**Проблема:** Колонки `session_id`/`sessionId` в таблицах `session_metrics` и `session_trades` расходились с Entity, из-за чего TypeORM вызывал `column "session_id" does not exist`, сессии не создавались, метрики не обновлялись.

**Решение:**
- Приведены SQL-скрипты (`backend/src/sql/createTables.sql`) к snake_case (`session_id`).
- Убедились, что `SessionMetrics`/`SessionTrade` используют те же имена столбцов.
- После обновления нужно выполнить миграцию: `ALTER TABLE session_metrics RENAME COLUMN "sessionId" TO session_id;` и аналогично для `session_trades`, либо пересоздать БД.

**Результат:**
- ✅ `SessionManager.createSession` успешно сохраняет данные
- ✅ `recordTrade`/`updateSessionMetrics` перестали падать
- ✅ API `/api/sessions/...` возвращает метрики без ошибок

### 6️⃣ **Восстановление сессий после перезапуска сервера**

**Проблема:** После перезапуска сервера открытые позиции терялись. Если позиция закрылась во время простоя (сработал TP/SL), она оставалась в БД как "открытая", но не отображалась в интерфейсе. PnL таких позиций не учитывался.

**Решение:**
- Добавлена автоматическая восстановление последней активной сессии при старте сканера
- Реализована валидация восстановленных позиций (проверка возраста, удаление старых)
- Добавлена проверка позиций против текущего рынка для выявления "фантомных" позиций
- Автоматическое закрытие позиций, которые должны были закрыться во время простоя с подсчётом PnL
- Добавлено поле `direction` в `session_trades` для корректного восстановления направления позиции

**Компоненты:**
- `SessionManager.restoreLastActiveSession()` — восстановление сессии из БД
- `SessionManager.restoreAndValidateOpenPositions()` — загрузка и валидация позиций
- `ExecutionManager.restorePosition()` — восстановление позиции в Redis
- `ExecutionManager.validateAndClosePhantomPositions()` — проверка и закрытие фантомных позиций
- Обновлённый `scanner.bootstrap.ts` с логикой восстановления

**Результат:**
- ✅ Сессии восстанавливаются после перезапуска (если не старше 24 часов)
- ✅ Открытые позиции загружаются из БД в Redis
- ✅ Фантомные позиции автоматически закрываются с расчётом PnL
- ✅ Старые позиции (>7 дней) удаляются автоматически
- ✅ Полная история сохраняется в БД

Подробнее: `backend/docs/SESSION_RESTORATION.md`

### Интеграция IDEAL_EXECUTION_PROFILE

**В компоненте настроек бэктеста:**

```typescript
// Переключатель "Идеальный режим (без комиссий)"
const idealMode = ref(false);

const executionProfile = computed(() => {
  if (idealMode.value) {
    return {
      tradingFeeRate: 0,
      leverage: 1,
      slippageBps: 0,
      confirmWindowSize: 1,
      maxConfirmationAttempts: 1
    };
  }
  // Или использовать дефолтный профиль
  return undefined;
});
```
