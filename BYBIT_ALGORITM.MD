Единый Комплексный План: Разработка Высокопроизводительной Системы Загрузки и Обработки Исторических Данных для Мульти-Биржевого Бектестинга

Цель: Создать масштабируемую и надежную систему для загрузки исторических OHLCV данных с бирж OKX и Bybit, способную эффективно обрабатывать большие объемы данных (3+ года для 300+ фьючерсных пар) без превышения API лимитов. Интегрировать эту систему в существующее веб-приложение для бэктестинга.

I. Общая Архитектура Системы Загрузки Данных

Многоуровневая Система Задач (BullMQ):

Мета-задачи: Крупные операции, такие как "Портфельный Бектест" или "Полная Синхронизация Данных для Биржи X".

Задачи Планирования/Координации: Воркеры для мета-задач анализируют требуемый объем данных и порождают атомарные задачи на загрузку.

Атомарные Задачи Загрузки: FETCH_CANDLES_FOR_PAIR (параметры: exchange, symbol, timeframe, startDate, endDate). Каждая такая задача отвечает за загрузку полного диапазона свечей для одной конкретной пары/таймфрейма.

Задачи Обновления Метаданных: FETCH_TRADING_PAIRS (параметр: exchange).

Сервисы API для Каждой Биржи:

OkxApiService.ts: Существующий сервис, инкапсулирующий логику OKX API.

BybitApiService.ts: Новый сервис для логики Bybit API V5.

Глобальные, Redis-based Rate Limiters:

okxGlobalRateLimiter: Экземпляр SmartRateLimiter (состояние в Redis), настроенный на лимиты OKX (30 зап/сек).

bybitGlobalRateLimiter: Экземпляр SmartRateLimiter (состояние в Redis), настроенный на лимиты Bybit (115-120 зап/сек).

Все API вызовы из сервисов (OkxApiService, BybitApiService) проходят через соответствующий глобальный RateLimiter. Это обеспечивает координацию между всеми воркер-процессами BullMQ.

Конфигурируемые Воркеры BullMQ:

Отдельные воркеры (или типы обработчиков в одном воркере) для разных типов задач.

Настраиваемая concurrency для воркеров, обрабатывающих задачи FETCH_CANDLES_FOR_PAIR, для управления количеством одновременно активных "загрузчиков".

Унифицированное Хранилище Данных (PostgreSQL + TypeORM):

Модели TradingPair и Candle включают поле exchange для различения данных с разных бирж.

DataService.ts абстрагирует операции с БД, учитывая exchange.

II. Логика Работы Оптимизированного Алгоритма Загрузки Свечей (на примере Bybit)

BybitApiService.getHistoricalCandlesForSymbolBybit(params):

Вход: symbol, category, interval, targetStartDateMs, targetEndDateMs.

Выход: Массив свечей за указанный диапазон или ошибка.

Процесс (пагинация):

Инициализация: currentBatchEndTimeMs = targetEndDateMs, allKlines = [].

Цикл (пока currentBatchEndTimeMs >= targetStartDateMs и есть данные):
a. Ожидание слота Rate Limiter'a: await bybitGlobalRateLimiter.waitForSlot();
b. Формирование запроса к Bybit API /v5/market/kline:
* symbol, category, interval.
* end = currentBatchEndTimeMs.
* limit = BYBIT_MAX_KLINES_PER_REQUEST (1000).
* start можно не указывать или рассчитать как currentBatchEndTimeMs - (limit * interval_ms), но не ранее targetStartDateMs.
c. Выполнение API запроса (через axios или аналогичный HTTP клиент).
d. Запись факта запроса в Rate Limiter: bybitGlobalRateLimiter.recordRequest();
e. Обработка ответа:
* Успех (HTTP 200, retCode: 0):
* Извлечь klines из response.data.result.list.
* Если klines пуст: завершить цикл для этой пары.
* Добавить klines в allKlines (в начало).
* oldestTsInBatch = timestamp_самой_старой_свечи_из_klines.
* Если oldestTsInBatch < targetStartDateMs ИЛИ klines.length < BYBIT_MAX_KLINES_PER_REQUEST: завершить цикл.
* currentBatchEndTimeMs = oldestTsInBatch - 1; (для следующего запроса).
* Ошибка API (включая 429, если RateLimiter не предотвратил, или другие ошибки):
* Запустить механизм retry (например, 3-5 попыток с экспоненциальной задержкой: 1s, 2s, 4s...).
* Перед каждой повторной попыткой также вызывать bybitGlobalRateLimiter.waitForSlot().
* Если все попытки неудачны: логировать ошибку, вернуть ошибку/пустой массив.

Пост-обработка: Отфильтровать allKlines по точному диапазону [targetStartDateMs, targetEndDateMs], отсортировать.

Вернуть результат.

III. Отличия Нового Алгоритма (Bybit) от Старого (OKX)

Максимальное количество свечей на запрос:

Bybit: 1000.

OKX: 300.

Влияние: Bybit требует ~3.3 раза меньше API запросов для того же объема данных, что значительно повышает скорость загрузки для одной пары.

Параметры пагинации API:

Bybit: start (мс), end (мс, включительно), limit. Логика: currentEnd = oldest_ts_in_batch - 1ms.

OKX: before (мс, эксклюзивно), after (мс, эксклюзивно), limit. Логика: currentBefore = oldest_ts_in_batch.

Влияние: Требуется разная логика обновления параметров для следующего запроса в цикле пагинации.

Rate Limits и их обработка:

Bybit: 120 зап/сек (Standard API, Market Data).

OKX: 30 зап/сек (с API ключом).

Влияние: SmartRateLimiter должен быть сконфигурирован с разными параметрами для каждой биржи. Bybit позволяет значительно более интенсивную параллельную загрузку (если concurrency воркеров это позволяет).

Структура эндпоинтов и ответов API:

Разные URL, имена полей в запросах и ответах.

Влияние: Требуются отдельные функции-адаптеры в BybitApiService и OkxApiService.

Получение списка торговых пар:

Bybit: /v5/market/instruments-info с параметром category (linear, inverse).

OKX: Другой эндпоинт (например, /api/v5/public/instruments с instType=SWAP/FUTURES).

Влияние: Отдельные функции в соответствующих API сервисах.

V. Управление API Лимитами при Массовой Загрузке (Ключевые Принципы)

Декомпозиция Задач: Портфельные операции (300+ пар) разбиваются в BullMQ на множество атомарных задач FETCH_CANDLES_FOR_PAIR.

Конкурентность Воркеров: BullMQ concurrency (например, 5-20) определяет, сколько задач FETCH_CANDLES_FOR_PAIR одновременно активны и могут пытаться сделать API вызов.

Глобальный Redis-based RateLimiter:

Каждый активный воркер, прежде чем его задача FETCH_CANDLES_FOR_PAIR сделает реальный API вызов (через OkxApiService или BybitApiService), обращается к соответствующему глобальному, Redis-based SmartRateLimiter (okxGlobalRateLimiter или bybitGlobalRateLimiter).

RateLimiter либо немедленно разрешает запрос (если лимит не превышен), либо заставляет задачу асинхронно "подождать" необходимое время.

Это гарантирует, что суммарное количество запросов от всех воркеров к одной бирже не превысит ее лимиты (например, 120 зап/сек для Bybit).

Эффективное Использование Ресурсов: Пока одни задачи ожидают в RateLimiter'е или ответа от API, CPU может быть использован другими задачами (парсинг, запись в БД) или другими воркерами.

Отсутствие "ручных" задержек: Логика sleep() не нужна в коде загрузки пар. RateLimiter сам управляет задержками.

Этот всеобъемлющий план создает надежную, масштабируемую архитектуру для работы с несколькими биржами и большими объемами данных, с акцентом на соблюдение API лимитов и максимальную производительность. Самым значительным изменением для существующей системы (помимо добавления логики Bybit) будет переход на Redis-based RateLimiters для обеспечения корректной координации между несколькими воркер-процессами.
